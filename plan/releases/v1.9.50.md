## Highlights

**Two amendments to 1.9.49's folder-identity injection, from the fleet review before it rolled.**

- **An `agent.config` env entry can now reference the folder's credential.** In 1.9.49 the rc
  landed *after* `agent.config.env` / `settings.agentEnv` expanded, so an entry such as
  `"CLAUDE_MCP_FLIGHTDESK_AUTHORIZATION": "Bearer ${FLIGHTDESK_API_KEY}"` expanded to `Bearer ` and
  the FlightDesk MCP server in the job would have failed auth. The rc is now applied before the
  expansion loop, so it is referenceable, and again after it, so those layers still cannot replace
  it. Precedence for the rc's own names is unchanged.
- **`organizationId` in the rc now reaches the job as `FLIGHTDESK_ORGANIZATION_ID`.** Once the
  CLI takes its key from the environment it never opens the folder file, so an org scope in the
  rc was silently lost in 1.9.49 — the agent would have fallen back to the token-scoped org. The
  name is also refused from a dispatch's `external_meta.env`, like the other two.

Additive, no migration, no new settings. The fleet can re-land its MCP-header line against this
version.

## Verification

Two new cases in `npm run test:flightdesk-dispatch`: an `agent.config.env` value of
`Bearer ${FLIGHTDESK_API_KEY}` expands to the rc's key (it expanded to `Bearer ` under 1.9.49's
ordering), and an rc with `organizationId` yields `FLIGHTDESK_ORGANIZATION_ID`, referenceable
from `agent.config.env` and not replaceable by it. Full suite passes. On-box check on shi is as
for 1.9.49, plus `env | grep ^FLIGHTDESK_ORGANIZATION_ID` and a working `flightdesk` MCP call
once the fleet's header line is back.
