## Highlights

**Heartbeats can run on a cron schedule in a timezone.**

- A heartbeat can now be scheduled with a standard 5-field cron expression and an IANA timezone,
  e.g. `0 5 * * 2-5` in `America/Puerto_Rico` for 05:00 Tuesday–Friday. Duties that should only
  run on certain weekdays no longer have to check the day and exit.
- Interval, daily-time and minute-offset heartbeats work exactly as before. A heartbeat uses one
  schedule type or the other: sending a cron expression together with interval fields, an invalid
  expression, an unknown timezone, or an expression that can never fire is rejected with a clear
  error. A cron schedule without a timezone uses the server's.
- Daylight saving is handled: a local time skipped when the clock jumps forward runs once at the
  next valid time, and one that happens twice when the clock falls back runs once.
- All stored times stay in UTC; the timezone only decides which local times match.
- `create_heartbeat` and `update_heartbeat` accept `cron_expression` and `timezone`;
  `list_heartbeats` returns them with `next_run_at` and the next three runs.

**The Heartbeats page has a schedule picker.**

- Choose Interval, Daily at a time, or Weekdays / cron. Weekday checkboxes and a time write the
  cron expression for you, and the expression can also be edited directly.
- A timezone dropdown defaults to the server's timezone, and the next three runs are shown in that
  timezone and in UTC, both while editing and on each cron heartbeat's card.

**A restart can no longer run the same heartbeat slot twice.**

- Queueing a heartbeat's job and scheduling its next run used to be two separate steps, so a
  restart between them made the slot run again once its job finished. They are now one database
  transaction. A slot missed while the server was down still runs once when it comes back.

## Verification

- `npm run ci:server` includes the new `test:heartbeat-schedule`: a Tue–Fri 05:00 heartbeat skips
  Sat–Mon, weekday-only schedules, both daylight-saving changes in America/New_York, validation
  errors, interval heartbeats producing the same next run as before, and once-per-slot firing
  across database-worker restarts (no double run, no missed run).
- The server smoke test covers the HTTP errors for a bad cron expression or timezone and the
  schedule preview; the existing heartbeat MCP test passes.
