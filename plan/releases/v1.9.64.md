## Highlights

**A run killed at its memory limit is reported as an OOM, even when the kernel record is missing.**

- FlightDesk retries an out-of-memory turn once with instructions to use less memory, and it
  recognises one from the failure text. A run that was SIGKILLed after reaching its own
  `MemoryMax`, with no kill counter or kernel record to confirm it, used to be reported as a plain
  error, so it got no memory hint.
- Such a run is now a *likely* OOM: its scope logged a `max` event, or its peak reached the limit.
  A run SIGKILLed while the shared agent slice was killing processes for memory is one too. Both
  are reported as OOMs, saying "likely OOM-killed by its per-run scope limit" or "…by the shared
  agent slice", and say another job may have been the victim when that is possible.
- A SIGKILL with no sign of memory pressure no longer uses wording that read as an OOM; it is
  reported as a kill of unknown cause.
- Memory evidence now includes the scope's peak usage.

**Agent scans warn when a repo's checkout is off its base branch.**

- Jobs read `agent.config` from the folder's checkout, so a main tree left on a task branch, or
  detached, runs whatever config that branch has. Each scan now logs a warning naming the repo,
  the branch it is on, and the command to put it back. Per-task worktrees are not affected.

## Verification

- `npm run ci:server` passes, including new cases in `test:agent-memory`: likely scope and slice
  OOMs, a plain kill that does not match FlightDesk's OOM pattern, and `memory.peak` read from
  cgroup fixture files.
- `test:worktrees` covers the branch warning against a real repo (on a task branch, detached, back
  on base, and a linked worktree); `test:job-concurrency` and `test:flightdesk-dispatch` pass.
- Run against this machine's 166 agent folders, the check took under a second and flagged only
  main checkouts left on feature branches.
