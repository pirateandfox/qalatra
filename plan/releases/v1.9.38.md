## Highlights

**Agents run in their own cgroup slice.** Qalatra Server, its MCP child, tmux sessions and every
agent it spawns all lived in one cgroup, and `memory.high` throttles reclaim across the whole cgroup
without distinguishing the hog from its neighbours. Because it throttles allocation so hard, a
runaway never climbs the rest of the way to `memory.max`, so nothing kills it — it stalls, and takes
the MCP endpoint with it. That is how two boxes stalled on 2026-08-31 with `:3457` timing out while
they otherwise looked healthy. Confirmed live before the change: one server cgroup held the server,
the MCP child, an agent's `claude`, and a whole tmux session under a single limit.

Agents now spawn through `systemd-run --user --scope --slice=qalatra-agents.slice`. Only the spawner
can do this — cgroup membership follows process ancestry, so configuration management cannot move an
agent into a slice. The launcher is probed rather than platform-detected: `systemd-run` needs a live
user manager and `XDG_RUNTIME_DIR`, not merely Linux, so macOS, non-systemd Linux and hosts without a
user manager all fall back to the previous spawn unchanged.

**Read tools accept a `fields` projection.** Every read that matched a task returned its full
`description` and `ai_context`. Both are freeform and `ai_context` is append-only by design, so
response size grew without bound and had nothing to do with the query being asked — and past the MCP
output cap the call *fails* rather than truncating. A status read that cost nothing 99 times failed
the 100th because of an unrelated task's history, observed at over 55,000 characters for a single
matched task from a caller that wanted about ten scalar fields.

`search_tasks`, `get_tasks_by_agent`, `list_agent_jobs` and `get_agent_job` now take `fields`.
Measured: `search_tasks` 2,794 → 256 bytes, `list_agent_jobs` 5,326 → 297. `get_agent_job` was the
other half of the same report — a failed job's error could not be read without dragging its prompt
through the cap — and its description now points at `fields="id,status,result,terminated_by"`.

`id` is always included, since a row the caller cannot then address is not actionable. An unknown
field name errors and lists the valid columns rather than being dropped: silently ignoring a typo
returns results that look complete while missing the column the caller was counting on.

## Linux servers: two steps, in this order

The slice only contains anything if it exists as a real unit with limits. An unknown `--slice=` is
auto-created as **transient with no limits**, which places agents correctly and constrains nothing —
so deploying this code without the slice moves agents *out* of the server's capped cgroup and into an
uncapped one. That protects the MCP endpoint but leaves a runaway agent unbounded, which is a worse
blast radius than before. Do not deploy the code first.

1. Set `qalatra_agent_slice_enabled: true` and the three `qalatra_agent_slice_memory_*` limits in
   the host's vars, sized from that box's own measured peak — not copied from another host — and
   apply the `mcp_hygiene` role on its own first. Older Qalatra ignores the slice, so this is safe to
   land ahead of the code.
2. Then update Qalatra normally. The server must restart to pick up the change: the launcher is
   probed once per server process and cached, so a server that keeps running never starts using it.

Verify placement rather than assuming deployment: `cat /proc/<agent-pid>/cgroup` should name
`qalatra-agents.slice`, and `systemctl --user show qalatra-agents.slice -p MemoryMax` must not report
`infinity`. Launch diagnostics on a failed job also report the active launcher, or "none".

Afterwards, re-measure both cgroups. The server's existing memory guardrail was sized around a
cgroup that contained the agents; with them moved out, both that limit and the slice's want revisiting
from their own observed peaks.

## Verification

The main risk identified for the slice work was that `systemd-run --scope` would leave the tracked
pid as systemd-run's, breaking the process-group kill that stops an agent together with everything it
spawned — which would have required naming each scope and stopping it through systemd. Measured on a
real box instead: `--scope` execs through, so the tracked pid remains the agent's own shell and still
leads its process group. A shell → agent → tool-subprocess tree had three cgroup members before the
kill and none after, through the existing path unchanged. No scope-stop path was needed.

Field projection is covered by a new test wired into the server CI gate, and a migration gap found
while testing it — the MCP-side schema had not been given the `runtime` column added in 1.9.37 — is
fixed, so either process can create it whichever opens the database first.
